dependency-cooldown: a must-have Claude Code setting ↗ 1 tip

  • dependency-cooldown setting blocks brand-new packages. The dependency-cooldown setting for Claude Code blocks package versions published less than 7 days ago from being installed through npm, pnpm or uv. It reduces the risk of supply chain attacks, protects against slopsquatting, and requires your permission if Claude tries. #

Post @lydiahallie Nov 13, 2026 Nov 19 edition

Make a Stop hook retry with exit code 2

A Stop hook can send Claude back to try again when a check fails, but only if the hook exits with code 2. Exit 2 returns Claude to retry with the hook's stderr; exit 1 is non-blocking, so Claude just finishes even though the check failed. #

@lydiahallie's talk "Rethinking Claude Code Best Practices": with newer models you can step out of the loop.   • ▶ 3:37 Cut generic warnings from CLAUDE.md. Remove generic instructions such as "Think hard and be thorough." or "IMPORTANT: always use the auth helper" from CLAUDE.md. Newer models don't need them, and clutter like this can derail them. Nov 20 edition Prompting & context › CLAUDE.md & instructions Talk by @lydiahallie #

  • ▶ 4:48 Describe Auto mode's trust boundaries in plain English. In `.claude/settings.json`, an `autoMode` block takes plain-English lists: `environment` (e.g. "Trusted cloud buckets: s3://acme-staging"), `allow` ("Deploying to staging is allowed") and `hard_deny` ("Never send code to third-party APIs"), each starting with `"$defaults"`. Nov 20 edition Talk by @lydiahallie #
  • ▶ 6:04 Hard-block commands with deny rules. Add a command to `permissions.deny` in `.claude/settings.json`, e.g. `"Bash(git reset --hard *)"`, to block it in the harness before the Auto mode classifier ever sees it. Nov 20 edition Talk by @lydiahallie #
  • ▶ 6:32 Rule of thumb for what to deny. If Claude could make a mistake you can take back (like git edits), leave it to the model. If you can't take it back (deleting something for good, exposing a secret, sending data outside), make it a deny rule. Nov 20 edition Talk by @lydiahallie #
  • ▶ 6:58 Deny reads of secrets. Add deny rules like `"Read(./.env)"` and `"Read(~/.ssh/**)"` so a compromised dependency can't trick Claude into reading or leaking your secrets. Nov 20 edition Talk by @lydiahallie #
  • ▶ 8:17 Turn on the shell sandbox. Nov 20 edition Verification & security › Sandboxing Talk by @lydiahallie #
  • ▶ 9:30 Run long tasks in a cloud session. Cloud sessions run on a fresh, isolated machine with your repo, keep going with your laptop closed, and keep local secrets such as `.env`, `~/.ssh` and GitHub tokens out of reach. Nov 20 edition Projects & cloud sessions › Long-running cloud sessions Talk by @lydiahallie #

  • ▶ 12:24 Run checks from lifecycle hooks. Use hooks to verify automatically: `PostToolUse` to lint after every edit, `TaskCompleted` to run a task's tests, and `Stop` to run the full suite at the end. Nov 20 edition Talk by @lydiahallie #
  • ▶ 13:02 Fail checks with exit 2, not exit 1. Make your check scripts exit with code 2 on failure. Exit 1, the common default, gets marked as completed; exit 2 sends Claude back to fix it. Nov 20 edition Talk by @lydiahallie #

  • MCP Events: agents that react without a prompt. With MCP Events, AI agents can subscribe to external events and react without waiting for a user prompt, for example starting a code review and running tests when a new PR arrives in a GitHub repository. Long-running cloud sessions 3

Post @dani_avila7 Nov 17, 2026 Nov 19 edition

Design long runs for surprise restarts

In Claude Projects and cloud sessions, the machine can restart without warning during hours-long processes, stopping containers, orchestrators and monitoring; completed work stays on disk but in-progress work can be lost. Make your orchestrator checkpoint after every step, resume from the last successful step, recover with a single script, check disk space and budget before each step, and alert you immediately when something stops. #
