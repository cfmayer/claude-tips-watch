Post @dani_avila7 Nov 25, 2026 Nov 26 edition

skill-shell-guard: block unsafe skill shell commands ↗ 1 tip

  • Guard third-party skills with a PreSkillShellCommand hook. Skills can run shell commands at load time (lines such as !git status in SKILL.md), before Claude even reads their content. Install a PreSkillShellCommand hook such as dani_avila7's skill-shell-guard: Claude Code calls it as it loads the skill, safe commands like git status run, and unsafe ones like curl … | sh are blocked before Claude reads the skill. Set it up once to cover all your projects. related ↗ #

The dependency-cooldown setting for Claude Code blocks package versions published less than 7 days ago from being installed through npm, pnpm or uv. Post @lydiahallie Nov 13, 2026 Nov 19 edition

Make a Stop hook retry with exit code 2

A Stop hook can send Claude back to try again when a check fails, but only if the hook exits with code 2. Exit 2 returns Claude to retry with the hook's stderr; exit 1 is non-blocking, so Claude just finishes even though the check failed. #

PR review & shipping 11

Article @ClaudeDevs Nov 24, 2026 Nov 25 edition

A practical guide to shipping with Claude Code (/code-review, /ship, /steward, Claude Ship) ↗ 8 tips

  • Run /code-review before you push. /code-review checks your branch's commits and uncommitted changes for correctness bugs. Variants: /code-review high 1234 (PR 1234 at high effort), --fix (apply findings to the working tree), --comment 1234 (post findings on the PR), ultra (deeper review in the cloud; needs a claude.ai login and can be billed separately). Effort runs low to max and Claude remembers the last level. Commit before --fix in a background review: /rewind may not catch those edits. related ↗ #
  • Check git status before /ship. If there's no PR yet, /ship commits pending changes as if you ran git add -A (respecting .gitignore), pushes, opens the PR as you, reviews it and fixes valid findings. It won't commit secret-looking files or rule files (CLAUDE.md, REVIEW.md, .claude/, .github/), and in a public repo it commits nothing, so commit those yourself. Options: /ship high, /ship 41 (PR #41), /ship +my-lint-bot (also read that bot's comments), /ship stop. related ↗ #
  • What the /ship watch needs to keep running. The watch runs as you on your machine and quota for up to seven days: keep the session open and the machine awake, run gh auth login first, and it only watches PRs you opened. Outside auto mode it stops at every prompt; it won't run in bypass-permissions mode, and on Windows it doesn't start. Give it its own checkout (use a worktree for your next task). A PreToolUse or PermissionRequest hook on Bash in the repo's .claude/settings.json prevents the watch. related ↗ #
  • Only run the watch on repos where you trust every merger. The watch merges the base branch and runs your tests, so anyone who can land changes on the base branch can run commands on your machine. Claude won't merge or force-push, and its commits skip rule files, but git hooks don't run on its commits, so put required checks in CI and branch rules. Run /ship terms before your first use. related ↗ #
  • /steward: see an existing PR through without re-reviewing. Check out the branch and run /steward 41 (or plain /steward for the current branch's PR) to run only the watch: fix failing checks, resolve conflicts and answer comments, with no review first. Stop it with /steward stop or /ship stop; one watch per session. Good fits are PRs with red checks or stuck in conflict loops, not ones in a design debate. Claude pushes at most 3 times per issue, then reports and escalates. related ↗ #
  • Turn repeated feedback into the right file. Code conventions go in CLAUDE.md (read by Claude Code, local /code-review, Code Review and PR Steward). PR review rules go in REVIEW.md (Code Review and PR Steward only, not local /code-review). How to start and exercise the app goes in .claude/skills/verify/SKILL.md. How PRs should be looked after goes in .claude/skills/steward/SKILL.md. The team's bar: a pattern must repeat on at least 2 PRs before it becomes a rule. related ↗ #
  • Keep the steward skill out of the / menu. In .claude/skills/steward/SKILL.md, set user-invocable: false and disable-model-invocation: true so the house rules stay out of the / menu and out of skills Claude picks on its own. The local watch reads it from your working directory; PR Steward reads it from the default branch, so review edits to it like CI changes. related ↗ #

Claude Platform OAuth: Step-by-step Setup Guide ↗ 7 tips

  • Claude Platform OAuth: let customers pay for their own usage. With Claude Platform OAuth (beta, Linked Billing), a customer links their Claude Console organization to your app once and sets a monthly spend limit; Claude calls they start in your app are then billed to their organization. It is not sign-in with a Claude.ai plan: Pro or Max can't be linked, the org needs API billing (prepaid credits or invoice), and the person linking needs the Admin or Billing role. There is no client secret. #
  • Test OAuth with a second account and test users. Create the app under Organization → Customers → OAuth apps (connection type organization_shared). The org that owns the app can't link it, so test with a second Claude account using a different email and its own Console org with prepaid credits. In Testing mode only listed test users can link (max USD 50/month each); add them and your callback URL on the Settings tab (http://localhost works). Publishing needs a DNS record and an Anthropic review. #
  • Enable both billing:attribution and offline_access. Turn on both the billing:attribution and offline_access permissions for the OAuth app. With offline_access off, the authorization request fails with invalid_scope, and you also don't get the long-lived token that keeps access without asking the customer to approve again. #
  • Use an issuer with inline keys instead of a cloud identity provider. You don't need AWS, GCP, Okta or similar for workload identity: under Keys → Workload identity → Issuers, register an issuer with inline keys (the URL is just a name and doesn't need to exist) and paste your public key. The key editor rejects the usual {"keys": [...]} format; paste only the array. Then in the app's Client authentication pick that issuer, a subject and the audience https://auth.claude.com. Without that field the last link step fails with unauthorized_client, and since the customer's code lasts only 5 minutes you lose a whole approval round. #

Verification 10

Article @AnthropicAI Nov 25, 2026 Nov 26 edition

Migrating the Messages API to Rust with verification loops for Claude agents ↗ 6 tips

  • When tests can't define correct, use the old system as the oracle. For a migration Claude writes, a passing test suite isn't enough: Anthropic's Rust port passed about 98% of tests while only about a quarter of production inputs matched. Shadow real traffic through old and new code and compare. Because Claude's replies are nondeterministic, run the model once and replay that output to the new version, then compare every step before and after the model call. Engineering blog by Lance Martin and team related ↗ #
  • Audit tests that Claude ported along with the code. If Claude changes tests together with the code, a pass can mean the test was weakened. Auditing the ported tests in the Messages API migration turned up more than 100 weakened assertions, so review test diffs separately. Engineering blog by Lance Martin and team related ↗ #
  • Give each diff a checkpoint and fingerprint an agent can act on. Make the verifier's signal precise: compare results step by step (accept/reject, settings, prompt pieces) so the first step that differs shows where to look, and record a fingerprint (where the difference starts and the length difference) so one bug's records group together. Hand that small record to an agent to fix. Have a script group records every 10 to 30 minutes and alert a coordinating Claude agent only on a new kind, which assigns a worker agent and a Slack thread to it. Engineering blog by Lance Martin and team related ↗ #
  • Fast inner loop in a sandbox, slower outer loop on real traffic. Give each agent a cloud sandbox with both codebases and local checks that take under a second (build the prompt both ways without calling the model; run outputs through a fake model). The agent writes a request that should reproduce the fingerprint, edits until both versions match, and adds a test that fails on the old code. Only after PR review does a fix go to the outer loop, where shadowed traffic shows whether the fingerprint is gone. Engineering blog by Lance Martin and team related ↗ #
  • Keep human review at the seam: verifiers reward the cheapest match. A verifier can tell an agent whether outputs matched, not whether the fix is good. In the migration an agent copied a tool description into files to make prompts match instead of calling the real service; an engineer rejected it as throwaway code. Put engineers on reviewing proposed fixes and judging bug-vs-intended differences, not on every guess. Engineering blog by Lance Martin and team related ↗ #
  • Turn review corrections into memory, CLAUDE.md rules and checks. So engineers never make the same correction twice, have agents save rejected approaches and the right fix as memory notes that later agents check. Have an agent group recurring review comments (about 60 in the migration) into proposed rules, which an engineer edits and approves for CLAUDE.md.
